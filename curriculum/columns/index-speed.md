# 100万行で、インデックスの有無を実測してみる

> [!NOTE]
> **これはコラムです。読まなくても演習は完了できます。** 演習03と内容が重なりますが、こちらは**数字を眺めて楽しむ**ためのものです。

## まず、桁を体で感じてほしい

SQL基礎の本文で「インデックスは本の索引と同じ」と書きました。それは正しいのですが、**比喩だけでは桁が伝わりません。**

実際に測った数字を置きます。演習で使う100万行のテーブルから、該当する100行を探した場合です。

| | 確認した行数 | かかった時間 |
|---|---|---|
| インデックス無し(`Seq Scan`) | 1,000,000 | 約 32 ミリ秒 |
| インデックス有り(`Bitmap Index Scan`) | 100 | 約 0.24 ミリ秒 |

**約130倍**でした。

> [!NOTE]
> **時間はあなたの環境では違う数字になります。** 上はそこそこ速いパソコンでの値で、PostgreSQL が並行処理を使ったため、全件走査側もかなり健闘しています。
>
> **環境によらないのは、左の列です。** 「100万行を全部確認した」か「100行だけ確認した」か。**これは何倍のマシンを使っても変わりません。**

## なぜ、少ない回数で済むのか

インデックスは、データを**あらかじめ並べ替えて**持っています。並んでいると、こういう探し方ができます。

1. 真ん中を見る。探しているものより大きいか、小さいか
2. 大きければ、**残り半分は見なくていい**
3. 残った半分の、また真ん中を見る
4. 繰り返す

1回ごとに候補が半分になります。100万を半分にし続けると、何回で1になるでしょうか。

```
1,000,000 → 500,000 → 250,000 → 125,000 → 62,500 → 31,250
→ 15,625 → 7,812 → 3,906 → 1,953 → 976 → 488 → 244
→ 122 → 61 → 30 → 15 → 7 → 3 → 1
```

**20回**です。

これが「ごく少ない回数で済む」の正体です。**辞書で単語を引くとき、あなたも無意識に同じことをしています。** 「か」で始まる単語を探すのに、1ページ目からめくる人はいません。

> [!NOTE]
> **正確には、実際のインデックス(B-tree)はもっと少ない回数で済みます。** 半分ずつではなく、1回で数百通りに枝分かれする構造だからです。100万行なら3〜4回程度。
>
> ただし**「1回ごとに候補が大きく減る」という考え方は同じ**なので、まずは上の halving のイメージで掴んでください。

## 桁が変わると、差はもっと開く

面白いのはここからです。行数を増やしたときの比較です。

| 行数 | インデックス無し(見る行数) | インデックス有り(見る回数) |
|---|---|---|
| 1,000 | 1,000 | 10 |
| 100,000 | 100,000 | 17 |
| 1,000,000 | 1,000,000 | 20 |
| 100,000,000 | 100,000,000 | 27 |

**行数が10万倍になっても、インデックス側は10回から27回にしか増えていません。**

これが「なぜか重い」が突然やってくる理由でもあります。**インデックスが無い側は、データが増えた分だけ素直に遅くなります。** リリース直後は1000行で0.03ミリ秒。1年後に100万行で32ミリ秒。3年後に1000万行なら320ミリ秒。**コードは1文字も変わっていないのに。**

そして厄介なのは、**この遅さが少しずつ進行すること**です。ある日突然壊れるのではなく、毎日ほんの少しずつ遅くなり、誰も気づかないまま、いつの間にか「なんか重いよね」になっています。

## 自分の手で測ってみる

演習03のデータベースがあれば、すぐ試せます。

```sql
\timing on

-- インデックスを消してから測る
DROP INDEX IF EXISTS idx_access_logs_user_id;
EXPLAIN ANALYZE SELECT * FROM access_logs WHERE user_id = 'u3391';

-- インデックスを作って、もう一度測る
CREATE INDEX idx_access_logs_user_id ON access_logs (user_id);
EXPLAIN ANALYZE SELECT * FROM access_logs WHERE user_id = 'u3391';
```

**`Seq Scan` が `Bitmap Index Scan` に変わる瞬間**と、`Execution Time` の桁が変わる瞬間を、自分の目で見てください。

> [!TIP]
> **`Index Scan` ではなく `Bitmap Index Scan` と出ます。** 該当行が複数あるときにPostgreSQLが選ぶ形で、これも索引を使っています。**`Index` の文字が入っているかどうかだけ見れば十分です。**
>
> また、インデックス無しのほうは **`Parallel Seq Scan`** と出ることがあります。複数の処理を並行させているだけで、**全部の行を見ていることは変わりません。**
>
> **数字は環境によって変わります。** あなたのパソコンで出た数字が、上の表と違っていて構いません。**大事なのは「何倍違ったか」と「何行を確認したか」です。**

## では、なぜ全部の列に張らないのか

本文でも触れましたが、もう少し具体的に。

インデックスは、**並べ替えた状態を別に持っている**ということです。つまり:

- **ディスクを余分に使う。** テーブルによっては、インデックスのほうが本体より大きくなることもあります
- **書き込みが遅くなる。** 1行足すたびに、インデックスも並べ直す必要があります。インデックスが5個あれば、5回
- **使われないインデックスは、コストだけ払っている**

3つ目が現場では厄介です。**「念のため張っておいた」インデックスが、実は一度も使われていない。** データベースには「どのインデックスが何回使われたか」を記録する仕組みがあり、実務ではそれを見て棚卸しします。

PostgreSQL なら、こう調べられます(演習のデータベースでも動きます)。

```sql
SELECT relname, indexrelname, idx_scan
FROM   pg_stat_user_indexes
ORDER BY idx_scan;
```

`idx_scan` が 0 のものは、**一度も使われていないインデックス**です。
