# クラウドとは何か

> [!NOTE]
> **これはコラムです。読まなくても演習は完了できます。** 気になったときに読んでください。

## 結局、あなたのコードはどこで動くのか

演習では、自分のパソコンでコードを動かしています。でも、あなたが作ったサービスを世界中の人に使ってもらうには、**24時間365日、電源が入っていて、インターネットにつながっているコンピュータ**が要ります。

自分のパソコンでは無理です。寝るときに閉じますし、持ち歩けば回線も切れます。

だから、**そういう役目専用のコンピュータ**を用意します。これを<mark>サーバー</mark>と呼びます。

## 昔は、本当に「箱を買って置いていた」

2000年代まで、Webサービスを始めるにはこうしていました。

1. サーバー用のコンピュータを買う(数十万円〜)
2. データセンター(電源と回線が安定した建物)に置く場所を借りる
3. OSを入れ、設定し、電源を入れる
4. 壊れたら、**現地に行って直す**
5. アクセスが増えたら、**もう1台買って、届くのを待つ**

問題は5番です。**「来週テレビで紹介されるので、アクセスが10倍になります」と言われても、サーバーは今日届きません。** かといって最初から10台買っておくと、普段は9台が遊んでいます。

## クラウドは「借りる」に変えた

<mark>クラウド</mark>とは、ものすごく大雑把に言えば **「他人が持っている巨大なデータセンターの一部を、必要なときだけ、必要な分だけ借りる仕組み」** です。

代表的なものが AWS(Amazon)、Azure(Microsoft)、Google Cloud です。

何が変わったか。

| | 昔(自前) | クラウド |
|---|---|---|
| 増やす | 買って、届くのを待つ(数週間) | **コマンド1行(数分)** |
| 減らす | 買ったものは減らせない | **消せば、その分の料金が止まる** |
| 壊れたら | 現地に行く | **新しいものを作り直す** |
| 初期費用 | 数十万〜数百万円 | **ほぼゼロ** |

**「壊れたら直す」ではなく「壊れたら作り直す」** という発想の転換が、いちばん大きな変化でした。1台1台を大事に育てるのではなく、**同じものをいつでも作り直せる状態にしておく。**

## Docker が出てくる理由

ここでようやく、演習で使っている `docker compose up -d` の話につながります。

「作り直せる状態にしておく」ためには、**「このコンピュータには何が入っていて、どう設定されているか」がファイルとして書かれていなければなりません。** 手作業で設定した内容は、作り直せないからです。

<mark>Docker</mark> は、まさにそれをやる道具です。SQL基礎の演習で使った `docker-compose.yml` を思い出してください。あのファイルには「PostgreSQL 17 を使う」「ユーザー名は app」と書いてありました。

**あのファイルさえあれば、誰のパソコンでも、クラウド上でも、まったく同じデータベースが立ち上がります。** 「私のパソコンでは動くんですが」という、ソフトウェア開発で最も有名な言い訳を消すために生まれた道具です。

## だから「サーバーには画面がない」

プログラミング基礎で **「サーバー側には `document` が存在しない」** という話をしました。ここにつながります。

クラウド上のサーバーは、**モニターもキーボードもつながっていません。** 画面を出す相手がいないので、画面という概念そのものがありません。

そして、そこを操作する唯一の方法が **コマンドライン** です。コマンドライン基礎の冒頭で「あなたが配属される先のサーバーには、そもそも画面がありません」と書いたのは、この意味です。

**入門フェーズの6トピックは、ばらばらの知識ではありません。** コマンドラインでサーバーを触り、Gitでコードを配り、HTTPで通信し、SQLでデータを取り出す — **クラウド上で動くサービスを保守するために、全部が要ります。**

## このカリキュラムでの使いどころ

本編の後半で、**あなたが直したシステムを実際にクラウドへデプロイ(配置)します。** 使うのは AWS の ECS Fargate という仕組みで、これは「Dockerで作った箱を、そのままクラウドで動かす」サービスです。

つまり、SQL基礎で `docker compose up -d` と打った経験が、そのまま本番のデプロイにつながっています。
