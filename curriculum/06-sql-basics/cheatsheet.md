## 取り出す(SELECT)

```sql
SELECT   id, name           -- どの列が欲しいか
FROM     users              -- どのテーブルからか
WHERE    is_premium = true  -- どの行に絞るか
ORDER BY registered_at DESC -- 何の順に並べるか
LIMIT    10;                -- 何件までか
```

| 部品 | やること | 詳しい説明 |
|---|---|---|
| `SELECT 列, 列` | 欲しい列を指定 | 本文「SELECT」 |
| `SELECT *` | 全部の列(**実務では避ける**) | 本文「SELECT」 |
| `FROM テーブル` | どのテーブルから | 本文「SELECT」 |
| `WHERE 条件` | 行を絞る | 本文「SELECT」 |
| `ORDER BY 列` | 昇順に並べる | 本文「SELECT」 |
| `ORDER BY 列 DESC` | **降順**に並べる | 本文「SELECT」 |
| `LIMIT 件数` | 上から何件まで | 本文「SELECT」 |
| `列 AS 別名` | 結果の列名を変える | 本文「集計する」 |

**処理される順番**: `FROM` → `WHERE` → `SELECT` → `ORDER BY` → `LIMIT`。**書く順番とは違います。**

## 条件の書き方(WHERE)

| 書き方 | 意味 |
|---|---|
| `= ` | 等しい(**SQLではイコール1つ**。`==` ではありません) |
| `<>` または `!=` | 等しくない |
| `>` `<` `>=` `<=` | 大小 |
| `AND` / `OR` / `NOT` | かつ / または / 否定 |
| `BETWEEN a AND b` | a以上b以下 |
| `IN ('a', 'b')` | どれかに一致 |
| `LIKE '%投稿%'` | 部分一致(`%` が任意の文字列) |
| `IS NULL` / `IS NOT NULL` | 値が無い / ある |

> [!WARNING]
> **`NULL` の比較に `=` は使えません。** `WHERE nickname = NULL` は、何にも一致しません(エラーにもなりません)。**必ず `IS NULL` を使ってください。** `NULL` は「値が無い」という状態であって、値ではないからです。

**文字列はシングルクォート `'` で囲みます。** ダブルクォート `"` は列名を囲む記号なので、間違えるとエラーになります。

## つなぐ(JOIN)

```sql
SELECT posts.id, users.name, posts.body
FROM   posts
JOIN   users ON posts.author_id = users.id;
```

| 書き方 | 相手が見つからない行は | 詳しい説明 |
|---|---|---|
| `JOIN`(= `INNER JOIN`) | **消える** | 本文「JOIN」 |
| `LEFT JOIN` | **残る**(相手側の列は `NULL`) | 本文「JOIN」 |
| `ON 条件` | どの列どうしを突き合わせるか | 本文「JOIN」 |

**「一覧から一部が消える」不具合の最頻出原因が `INNER JOIN` です。** 詳しくは本文と演習02。

## 集計する

| 書き方 | やること | 詳しい説明 |
|---|---|---|
| `COUNT(*)` | 件数 | 本文「集計する」 |
| `SUM(列)` | 合計 | 本文「集計する」 |
| `AVG(列)` | 平均 | 本文「集計する」 |
| `MAX(列)` / `MIN(列)` | 最大 / 最小 | 本文「集計する」 |
| `GROUP BY 列` | その列の値が同じものをまとめる | 本文「集計する」 |
| `HAVING 条件` | **グループにした後**で絞る | このチートシートのみ |
| `SELECT DISTINCT 列` | 重複を除いた値の一覧 | 演習03 |

**`WHERE` と `HAVING` の違い**: `WHERE` は**まとめる前**に行を絞り、`HAVING` は**まとめた後**にグループを絞ります。「投稿が3件以上あるユーザー」は `HAVING COUNT(*) >= 3` です。

## 速さを調べる(最重要)

| 書き方 | やること | 詳しい説明 |
|---|---|---|
| `EXPLAIN SELECT ...` | **どう実行するつもりか**を見る(実行しない) | 本文「インデックス」 |
| `EXPLAIN ANALYZE SELECT ...` | **実際に実行して**、かかった時間も見る | 本文「インデックス」 |
| `CREATE INDEX 名前 ON テーブル (列);` | インデックスを作る | 演習03 |
| `DROP INDEX 名前;` | インデックスを消す | このチートシートのみ |

**`EXPLAIN` の出力で見るところ**

| 出てきた文字 | 意味 |
|---|---|
| **`Seq Scan`** | 全件走査。**全部の行を見ている**(遅い可能性) |
| **`Parallel Seq Scan`** | 同じく全件走査。並行して読んでいるだけで、全部見ていることは変わらない |
| **`Index Scan`** | インデックスを使った |
| **`Bitmap Index Scan`** | インデックスを使った(該当行が多いときに選ばれる形) |
| **`Index Only Scan`** | インデックスだけで答えが出た。表を読みにすら行っていない |
| `rows=` | 見た(または見る予定の)行数 |
| `actual time=` | 実際にかかった時間(ミリ秒) |
| `Execution Time:` | 全体でかかった時間(ミリ秒)。**まずここを見る** |

**見分け方**: 名前は5種類ありますが、**`Index` の文字が入っていれば索引が使われています。** どの形になるかはデータベースが決めるので、最初は `Seq` か `Index` かだけ見れば十分です。

> [!IMPORTANT]
> **`Seq Scan` が常に悪いわけではありません。** 行数が少ないテーブルや、絞り込みが効かない条件では、全部読んだほうが速いことがあります。**インデックスを張ったのに使われない場合も、たいていは正しい判断です。数字を見てください。**

## 変える・消す・作る

```sql
INSERT INTO posts (id, author_id, body, likes, posted_at) VALUES ('p099', 'u1043', '新しい投稿', 0, now());
UPDATE posts SET likes = 100 WHERE id = 'p099';
DELETE FROM posts WHERE id = 'p099';
```

| 書き方 | やること | 詳しい説明 |
|---|---|---|
| `INSERT INTO テーブル (列, ...) VALUES (値, ...);` | 新しい行を作る | 演習05 |
| `UPDATE テーブル SET 列 = 値 WHERE 条件;` | 条件に合う行を書き換える | 演習05 |
| `DELETE FROM テーブル WHERE 条件;` | 条件に合う行を消す | 本文「変える・消す」 |

> [!CAUTION]
> **`UPDATE` と `DELETE` で `WHERE` を書き忘れると、全行が対象になります。** 確認は出ません。
>
> **身を守る手順**: まず同じ `WHERE` で `SELECT` を打ち、対象の行を目で見る。それから `SELECT ...` の部分だけを `DELETE` / `UPDATE` に書き換える。コマンドライン基礎の「`rm` の前に `ls`」と同じ考え方です。

## トランザクション

| 書き方 | やること | 詳しい説明 |
|---|---|---|
| `BEGIN;` | ここから「仮の変更」を始める | 本文「トランザクション」 |
| `ROLLBACK;` | `BEGIN` した時点まで、すべて巻き戻す | 演習05 |
| `COMMIT;` | ここまでの変更を確定する | 本文「トランザクション」 |

**`BEGIN` していない1文は、実行した瞬間に確定します。** 危険な変更をする前に、まず `BEGIN` を打つ癖をつけると事故を防げます。
