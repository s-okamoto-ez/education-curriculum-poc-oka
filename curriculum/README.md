## この6つが、1本の道になっている

ばらばらの知識に見えるかもしれませんが、そうではありません。

保守改修の現場で最も多い問い合わせは **「画面に出ているこの数字がおかしい」** です。その調査は、必ず同じ経路をたどります。

```
画面(HTML/CSS) → 通信(HTTP) → サーバーのコード(TypeScript) → SQL → データベース
```

**この経路を、端から端まで自分で追えるようにする。** それが入門フェーズのゴールです。どこか1区間でも読めないと、そこで調査が止まります。

コマンドラインとGitは、この経路のどこを触るときにも必要になる道具です。だから最初に置いています。

> [!NOTE]
> 使う言語は **TypeScript** ですが、このカリキュラムが約束しているのは「TypeScriptが書けるようになる」ことではありません。**配属先の言語が変わっても持ち越せるもの**を渡すことです。
>
> 実際、6トピックのうち5つ(計64時間)は最初から言語に依存しません。言語に依存するのはプログラミング基礎だけです。

## 全トピックに共通する進め方

1. **README を読む**(概念の理解)
2. **演習を、順番に進める** — 各演習は GitHub Issue として1つずつ配られます
3. **実行する前に、結果を予測して Issue にコメントする**
4. **実行して、結果を貼る**
5. **予測と違ったら、なぜ違ったかを一言書く**
6. チェックリストが埋まったら、自分の判断で Issue を Close する

Close に承認は要りません。ただし**講師は、Close された Issue のコメントに後から目を通します。** つまずいた形跡も含めて記録に残ることに意味があります。

**なぜ「予測してから実行」なのか**: 実務で毎回この手順を踏むわけではありません。ここでは意図的に立ち止まり、先に自分の理解を言葉にしてから答え合わせをすることで、**「分かったつもり」と実際の理解のズレ**に自分で気づけるようにしています。AIに聞けば結果は一瞬で分かりますが、それでは自分が何を分かっていないかは分からないままです。

> [!IMPORTANT]
> **演習の予測・回答をAIに考えさせる／書かせるのは禁止です。** 一方で、**分からない用語や概念をAIに聞いて調べるのは自由**です。
>
> 入門フェーズでは、**AIにコードを生成させることも禁止**しています。ここで手を貸してもらうと、他人のコードを読む力が育ちません。**本編に入ったら全面解禁します。**

## トピックの中身は共通の構成です

```
curriculum/<番号>-<トピック名>/
  README.md      教材本体。最初にこれを読む
  cheatsheet.md  コマンド・構文の早見表。忘れたらここ
  exercises/     演習の中身(Issueとして配られるもの)
  samples/       演習で使う題材(ログ、HTML、コード、DBなど)
  assets/        図・アイコン
```

演習Issueは、このリポジトリをテンプレートとして複製したときに、**全トピック分まとめて自動発行されます**(`.github/workflows/seed-issues.yml`)。各トピックのREADMEからは、Issueの元になった `exercises/` のファイルに直接リンクしています。**内容は同じものです。**

## 環境の準備

トピックによって必要なものが違います。**ターミナル・エディタ・Gitは [0. はじめに](00-getting-started.md) で用意済みのはずです。** それ以外は、必要になるトピックの冒頭で「入れる→確かめる」の手順を案内します。

| トピック | 必要なもの |
|---|---|
| 1〜3 | ターミナル(Windowsは **Git Bash**)、ブラウザ、エディタ(いずれも [0. はじめに](00-getting-started.md) で準備済み) |
| 4 | 上記 + **Node.js**(v22 以上、4のトピック内で案内) |
| 5 | 上記 + `curl`(標準で入っています) |
| 6 | 上記 + **Docker**(6のトピック内で案内) |

**環境構築でつまずいたら、そのまま Issue にコメントしてください。** 隠す必要はありません。むしろ、どこで詰まるかは教材を良くするための情報です。
